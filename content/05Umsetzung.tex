\section{Software}

    \subsection{Videoübertragung} % wie aufgenommen? wie gesendet? etc.
    Das Aufnehmen der Bilder erfolgt mittels der Raspberry Pi Kamera, die über die \ac{CSI}-Schnittstelle mit dem Raspberry Pi verbunden ist. Jedoch ist die Aufnahme und Übertragung dieser Bilder keine triviale Aufgabe. Die Bilder müssen in Echzeit aufgenommen, komprimiert und über das Netzwerk an den Client gesendet werden. Wie zuvor im Abschnitt \ref{sec:video_encoding_comparison} festgelegt, soll als Übertragungsprotokoll \ac{WebRTC} und als Codec H.264 verwendet werden, da es speziell für die Übertragung in Echtzeit entwickelt wurde und eine geringe Latenz bietet. 

    Eine eigene Implementierung des \ac{WebRTC} Protkolls wäre sehr aufwendig und würde nicht zum eigentlichen Ziel der Arbeit beitragen. Aufgrund dessen wird die Software \emph{MediaMTX} verwendet, welche eine einfache Schnittstelle für die Implementierung von \ac{WebRTC} bietet. MediaMTX ermöglicht es, die aufgenommenen Bilder der Kamera zu komprimieren und über das Netzwerk an den Client zu senden, ohne dass eine eigene Implementierung des \ac{WebRTC} Protokolls erforderlich ist. Ein weiterer Vorteil von MediaMTX ist, dass es im Falle er Pi Kamera direkt die Bilder von der Kamera aufnehmen und komprimieren kann, ohne dass die Bilder zuerst an die \ac{CPU} gesendet werden müssen, was die Latenz weiter reduzieren würde. Somit profitiert die Videoübertragung von den Hardwareencodern des Raspberry Pi, was zu einer deutlich geringeren Latenz führt.

    Damit die Kamera von MediaMTX erkannt und verwendet werden kann, muss sie in der Konfigurationsdatei von MediaMTX entsprechend konfiguriert werden. In Listing~\ref{lst:mediamtx_config} ist die Konfiguration der Kamera zu sehen. Hier werden die Quelle der Bilder, die Auflösung, die Bildrate und die Ausrichtung der Bilder festgelegt. Durch diese Konfiguration kann MediaMTX die Bilder der Kamera aufnehmen, komprimieren und über das Netzwerk an den Client senden. Aufgrund dessen, dass die Kamera verkehrt herum montiert ist, müssen die Bilder vertikal und horizontal gespiegelt werden, damit sie auf der Weboberfläche korrekt angezeigt werden.

    \begin{lstlisting}[caption={Konfiguration der Kamera in der \emph{MediaMTX} Konfigurationsdatei}, label={lst:mediamtx_config}]
cam:
    source: rpiCamera
    rpiCameraWidth: 1280
    rpiCameraHeight: 720
    rpiCameraFPS: 30
    rpiCameraVFlip: yes
    rpiCameraHFlip: yes
    \end{lstlisting}

    Die Weboberfläche kann sich mit dem \ac{WebRTC} Stream von MediaMTX verbinden und die Bilder in einem Video Element anzeigen. 

    \subsection{Fernsteuerung}
    Die Fernsteuerung des Fahrzeugs erfolgt über die Weboberfläche, die auf einem beliebigen Client, welcher sich im selben lokalen Netzwerk wie der Raspberry Pi befinden muss, geöffnet werden kann. Über die Weboberfläche können Steuerbefehle an das Backend gesendet werden, um die Bewegung des Fahrzeugs zu steuern. Die Steuerbefehle werden über die Websocket-Verbindung gesendet und vom Backend empfangen. Das Backend interpretiert die empfangenen Befehle und steuert entsprechend die Motoren des Fahrzeugs an, um die gewünschte Bewegung zu erreichen. \\
    Im Folgenden werden der Aufbau der Weboberfläche und die genauere Implementierung der Fernsteuerung beschrieben.

        Sobald der Joystick bewegt wird, wird die Eingabe erfasst und in der in Listing~\ref{lst:handle_move} gezeigten Funktion verarbeitet. Dabei werden die x- und y- Koordianten des Joysticks erfasst und in den Wertebereich von -100 bis 100 umgerechnet. Die Erfahrung hat hierbei gezeigt, dass es für die Steuerung des Fahrzeugs von Vorteil ist, wenn die Werte auf ein Vielfaches von fünf gerundet werden. Dies hat den Ursprung darin, dass der Joystick sehr empfindlich gegenüber minimalen Bewegungen ist. Vor allem bei der Verwendung auf einen Touchscreen, ist es schwierig, den Joystick permanent in der selben Position zu halten. 

        Durch die Umrechung in fünfer Schritte, kann vermieden werden, dass durch minimale Bewegungen ständig neue Befehle mit minimalen Abweichungen gesendet werden, was zu einem unruhigen und ruckligen Fahrverhalten führt. Stattdessen werden nur dann neue Befehle gesendet, wenn sich beide Werte um mindestes fünf Einheiten geändert haben. Somit kann weiterhin für eine präzise Steuerung gesorgt werden, ohne dass permanent neue Daten mit minimalen Abweichungen gesendet werden.

        \begin{lstlisting}[caption={Handler für Joystick-Bewegungen, um Steuerbefehle zu senden}, label={lst:handle_move}]
const handleMove = (event: any) => {
    const { x, y } = event

    const speed = Math.round(Math.round(y  * 100)/5)*5 // Convert to range -100 to 100
    const steering = Math.round(Math.round(x  * 100)/5)*5 // Convert to range -100 to 100
    if (speed === lastSpeed.current && steering === lastSteering.current) {
        return
    }
    lastSpeed.current = speed
    lastSteering.current = steering
    const jsonMessage = {
        id: 'drive_command',
        payload: {
            x: steering,
            y: speed,
        },
    }
    if (socket && isConnected) {
        socket.send(JSON.stringify(jsonMessage))
        console.log('Joystick move message sent:', jsonMessage)
    } else {
        console.error('WebSocket is not connected')
    }
}
        \end{lstlisting}

    Auf dem serverseitigen Backend wird zur Implementierung des Websockets die Python-Bibliothek \emph{PySide6} und die darin enthaltene \emph{QtWebSockets} Klasse verwendet. Diese ermöglicht es, eine Websocket-Verbindung zu erstellen und zu verwalten, um die Kommunikation zwischen der Weboberfläche und dem Backend zu ermöglichen. Auf der Weboberfläche wird TypeScript verwendet, um die Verbindung zum Websocket herzustellen und die Daten zum Senden und Empfangen zu verarbeiten bzw. vorzubereiten.
    
    Die Verarbeitung der Nachrichten erfolgt im Backend durch eine \emph{Handle\_Message} Funktion, welche die empfangen Nachrichten zunächst in Id und Payload aufteilt. Anhand der Id kann festgestellt werden, um welche Art von Nachricht es sich handelt. Sobald eine Nachricht mit der Id "drive\_command", wie zuvor in Listing~\ref{lst:handle_move} gezeigt, empfangen wird, werden die darin enthaltenen Parameter extrahiert und an den die entsprechende Methode des Controllers übergeben, um die Motoren des Fahrzeugs entsprechend zu steuern.

    Die Steuerung der Motoren wird durch die \emph{drive\_joystick} Methode des Controllers realisiert, welche die x- und y- Werte der Joystick-Eingabe entgegennimmt und in entsprechende Befehle für die Motoren umwandelt. In Listing~\ref{lst:drive_joystick} ist die Implementierung der \emph{drive\_joystick} Methode zu sehen. Die x-Koorodinate wird als Lenkungswert interpretiert, während die y-Koordinate als Geschwindigkeitswert interpretiert wird. Anhand dieser Werte werden die Zielgeschwindigkeiten für den linken und rechten Motor berechnet, um die gewünschte Bewegung des Fahrzeugs zu erreichen. Die berechneten Zielgeschwindigkeiten werden anschließend an die Motoren übergeben, um die Bewegung des Fahrzeugs entsprechend zu steuern.

    \begin{lstlisting}[caption={Funktion zur Steuerung des Fahrzeugs über den Joystick}, label={lst:drive_joystick}]
def drive_joystick(self, x: float, y: float) -> None:
    x = self._clamp(x, -100.0, 100.0)
    y = self._clamp(y, -100.0, 100.0)

    left = y + x
    right = y - x

    self._left_target = self._clamp(left, -100.0, 100.0)
    self._right_target = self._clamp(right, -100.0, 100.0)

    self._apply_ramp()
    \end{lstlisting}

    Die Zielgeschwindigkeiten für die Motoren werden in den Variablen \emph{\_left\_target} und \emph{\_right\_target} gespeichert. Diese Zielgeschwindigkeiten werden jedoch nicht direkt an die Motoren übergeben, sondern durch die Funktion \emph{\_apply\_ramp} verarbeitet, um eine sanfte Beschleunigung und Verzögerung zu gewährleisten. Dies hat den Grund, dass das abrupte Beschleunigen oder Bremsen zu Instabilitäten innerhalb des Stromkreises und dadurch einem Ausfall des Raspberry Pi geführt hat. Gleichstrommotoren können bei plötzlichen Änderungen der Geschwindigkeit hohe Ströme ziehen oder beim Bremsen induzieren, was zu Spannungsschwankungen im System führen kann. Darauf reagiert vor allem der Raspberry Pi mit einem automatischen Herunterfahren, um Schäden zu vermeiden. 

    In der Regel würde man Stützkondensatoren verwenden, um diese Schwankungen auszugleichen. Aufgrund von Zeitmangel wurde sich jedoch dafür entschieden, dieses Problem softwareseitig zu lösen. Die Funktion \emph{\_apply\_ramp} sorgt dafür, dass die Geschwindigkeit der Motoren schrittweise erhöht oder verringert wird, anstatt sofort auf die Zielgeschwindigkeit zu springen. Dadurch werden die Stromspitzen vermieden, die durch plötzliche Änderungen der Geschwindigkeit verursacht werden können, wodurch das Ausfallen des Raspberry Pi verhindert wird. Sobald die Geschwindigkeiten durch die Funktion \emph{\_apply\_ramp} berechnet wurden, werden diese an die Motoren übergeben. In Listing~\ref{lst:apply_output} ist die Funktion \emph{\_apply\_output} zu sehen, welche die berechneten Zielgeschwindigkeiten an die Motoren übergibt, um die Bewegung des Fahrzeugs entsprechend zu steuern.

    Damit der Motortreiber die Motoren entsprechend ansteuern kann, muss die Richtung und die Geschwindigkeit der Motoren festgelegt werden. Die Richtung wird durch die Steuerung der Pins \emph{right1}, \emph{right2}, \emph{left1} und \emph{left2} festgelegt, während die Geschwindigkeit durch die Steuerung der \ac{PWM}-Signale an den Pins \emph{rightpwm} und \emph{leftpwm} festgelegt wird. Der \emph{TB6612FNG} verfügt wie zuvor erwähnt über eine H-Brücke, welche es ermöglicht, die Richtung der Motoren durch die Steuerung der Pins festzulegen. Durch das Anlegen von HIGH oder LOW an diesen Pins kann die Drehrichtung der Motoren gesteuert werden. Die Geschwindigkeit wird durch die Steuerung der \ac{PWM}-Signale festgelegt, welche die Leistung, die an die Motoren geliefert wird, regulieren. Durch die Anpassung des Duty Cycles der \ac{PWM}-Signale kann die Geschwindigkeit der Motoren entsprechend erhöht oder verringert werden. Hierzu wechselt \ac{PWM} sehr schnell zwischen HIGH und LOW. Ein höherer Duty Cycle bedeutet, dass die Motoren im Mittel Leistung erhalten da mehr Strom fließt und somit schneller drehen, während ein niedrigerer Duty Cycle bedeutet, dass die Motoren weniger Leistung erhalten und somit langsamer drehen. Aufgrund der Tatsache, dass die Motoren träge sind reagieren sie nicht auf die schnellen Wehchsel der \ac{PWM}-Signale, sondern nehmen die durchschnittliche Leistung über die Zeit wahr, was zu einer entsprechenden Geschwindigkeit führt.

    Der Motortreiber verfügt über zwei Kanäle, jedoch kann pro Kanal ein maximaler Strom von 1,2 A fließen. Da die Motoren jedoch dauerhaft einen Strom von 1,8 A ziehen können, ist es notwendig, beide Kanäle des Motortreibers parallel zu schalten, um die benötigte Stromstärke für die Motoren bereitzustellen, damit der Motortreiber nicht beschädigt wird. Durch das Parallelschalten der Kanäle wird die maximale Stromstärke, die an die Motoren geliefert werden kann, auf 2,4 A erhöht, was ausreichend ist, um die Motoren mit der benötigten Leistung zu versorgen.


    \begin{lstlisting}[caption={Funktion zur Ansteuerung der Motoren}, label={lst:apply_output}]
def _apply_output(self, left_speed: float, right_speed: float) -> None:
    left_fwd = left_speed >= 0
    right_fwd = right_speed >= 0

    # Right motor direction 
    self.drivers.write(self.right1, not right_fwd)
    self.drivers.write(self.right2, right_fwd)
    self.drivers.setup_pwm(self.rightpwm, frequency=5000, duty_cycle=abs(right_speed))

     # Left motor direction 
    self.drivers.write(self.left1, left_fwd)
    self.drivers.write(self.left2, not left_fwd)
    self.drivers.setup_pwm(self.leftpwm, frequency=5000, duty_cycle=abs(left_speed))

    self.last_set_speed = max(abs(left_speed), abs(right_speed))
    \end{lstlisting}
    

     \subsection{Notbremsung} % wir könnten den Scheiß richtig kompliziert machen, wenn wir berechnen wie schnell sich der Abstand zum Hindernis reduziert, wie schnell das Fahrzeug ist und wie weit das Hindernis entfernt ist. Weil wenn man hinter einem fahrenden Auto fährt und man nur Geschwindigkeit und Abstand misst, wird die Notbremsung vielleicht ungewollt ausgelöst. Oder wir sagen wir beachten nur 
    In diesem Projekt werden Ultraschallsensoren als Frühwarnsystem zur Hinderniserkennung eingesetzt. Die Sensoren werden so positioniert, dass sie den Bereich vor dem Fahrzeug überwachen können. Wenn ein Hindernis erkannt wird und die Gefahr einer Kollision besteht, kann automatisch eine Notbremsung eingeleitet werden, um diese zu verhindern. 
    Ultraschallsensoren sind für diesen Anwendungsfall besonders geeignet, da sie zuverlässig Entfernungen messen können, selbst wenn die Sichtverhältnisse schlecht sind, beispielsweise bei Dunkelheit, Staub oder Nebel. Zudem sind sie kostengünstig und einfach zu integrieren, was sie zu einer idealen Wahl für die Hinderniserkennung in diesem Projekt macht.

    Eine Notbremsung wird durchgeführt, wenn ein Hindernis eine potenzielle Kollisionsgefahr darstellt. Die gemessene Entfernung zu diesem Hindernis wird unter Berücksichtigung der aktuellen Geschwindigkeit des Fahrzeugs ausgewertet. Dadurch kann ermittelt werden, ob eine Kollision wahrscheinlich ist.
    Die Auswertung der gemessenen Entfernung erfolgt durch die Berechnung des Bremswegs, der anhand der aktuellen Geschwindigkeit berechnet wird. Hierzu wird die Formel für eine Notbremsung herangezogen. Die Formel für die Berechnung des Bremswegs bei einer normalen Bremsung kann in diesem Fall vernachlässigt werden, da es sich um die Implementierung einer Notbremsung handelt. Für eine Notbremsung wird folgende Formel verwendet: 
    \begin{equation}
        s = \frac{v}{10} \cdot \frac{v}{10} \cdot 0.5
    \end{equation} 
    wobei \( s \) dem Bremsweg in Metern und \( v \) der Geschwindigkeit in km/h entspricht. \\
    Dabei wird der Bremsweg um 50 \% reduziert, um die schnellere Reaktion und stärkere Betätigung des Bremspedals bei einer Notbremsung zu berücksichtigen \cite{BremswegBerechnen}. 
    
    Für gewöhnlich wird für den tatsächlichen Anhalteweg eines Fahrzeugs zusätzlich zum Bremsweg auch die Reaktionszeit berücksichtigt, die der Fahrer benötigt, um auf die Gefahr zu reagieren und die Bremsung einzuleiten. Da in diesem Fall jedoch eine Notbremsung durch die Software automatisch ausgelöst wird, fällt diese Reaktionszeit deutlich geringer aus. Ein weiterer Aspekt der berücksichtigt werden muss, ist die Tatsache, dass das Fahrzeug aufgrund seines geringen Gewichts einen deutlich kürzeren Bremsweg hat als ein echtes Fahrzeug. Daher wird die Differenz zwischen dem Bremsweg eines echten Fahrzeugs und diesen Fahrzeugs als Puffer für die Reaktionszeit und die Bremsverzögerung genutzt, um sicherzustellen, dass die Notbremsung nicht zu spät ausgelöst wird.

    Damit das Fahrzeug tatsächlich eine Notbremsung durchführt, muss die Software in der Lage sein, die gemessene Entfernung zum Hindernis mit dem berechneten Bremsweg zu vergleichen. Hierzu wird periodisch die Funktion \emph{emergency\_stop} aufgerufen (siehe Listing~\ref{lst:emergency_stop}), welche die gemessene Entfernung zum Hindernis aktualisiert und mit dem berechneten Bremsweg vergleicht. Sobald die gemessene Entfernung kleiner oder gleich dem berechneten Bremsweg plus einem zusätzlichen Puffer ist, wird die Notbremsung ausgelöst, indem die Motoren des Fahrzeugs gestoppt werden. Da die Methode periodisch und asynchron aufgerufen wird, kann die Methode die Eingabe des Benutzters überschreiben, um eine Kollision garantiert zu vermeiden.

     \begin{lstlisting}[caption={Funktion zur Durchführen einer Notbremsung}, label={lst:emergency_stop}]
def emergency_stop(self) -> None:
    distance = self._update_distance()
    speed = self.controller.get_current_speed() * 3.6
    break_distance = (
        (speed / 10) * (speed / 10) * 0.5 * self.emergency_stop_brake_scale
    )
    driving_backward = self.last_drive_y < 0

    if distance <= self.emergency_stop_min_distance_cm:
        self.emergency_stop_active = True
        if not driving_backward:
            self.break_time = time.time()
            self.controller.stop()
        return

    if break_distance + self.emergency_stop_brake_margin_cm >= distance and not driving_backward:
        self.break_time = time.time()
        self.emergency_stop_active = True
        self.controller.stop()
        return

    if self.emergency_stop_active:
        if speed == 0 and (time.time() - self.break_time) > 3:
            self.emergency_stop_active = False
        return
        \end{lstlisting}

        \subsubsection{Vision Worker}
        Die Verarbeitung von Bildern ist eine rechenintensive Aufgabe. Ein Ausführen im Hauptthread des Programms, also ein blockierender Aufruf, wäre nicht akzeptabel, da so die Reaktionsfähigkeit der Software stark beeinträchtigt werden würde. Aufgrund dessen werden alle bildverarbeitenden Aufgaben in einen separaten Thread, den sogenannten \emph{Vision-Worker} ausgelagert. Dieser Thread läuft parallel zum Hauptthread und ist ausschließlich für die Verarbeitung der Bilder zuständig. Der Worker kann sich kontinuierlich die neuesten Bilder vom MediaMTX Stream holen und diese verarbeiten. Dieses Bild kann dann verarbeitet und der Steuerbefehl per QT-Signal an den Hauptthread gesendet werden, um die Bewegung des Fahrzeugs entsprechend zu steuern. 

        \subsubsection{Verarbeitung}
        Standardmäßig sind die Bilder der Kamer im RGB Farbraum. Für die Verarbeitung der Bilder ist dies jedoch nicht optimal, da die Farbinformationen bei RGB mit dem Helligkeitswert vermischt sind, was die Erkennung der orangenen Farbe erschwert. Daher werden die Bilder zunächst in den HSV Farbraum umgewandelt, da hier die Farbinformationen (Hue) von den Helligkeitsinformationen (Value) getrennt sind, was die Erkennung der orangen Farbe erleichtert. 

        Damit nun die orangene Linie innerhalb des Bildes erkannt werden kann, muss das Bild in ein Binärbild umgewandelt werden, in welchem die Pixel mit orangenem Farbwert weiß und alle anderen Pixel schwarz sind. Hierzu wird eine Farbschwelle definiert, welche die unteren und oberen Grenzen für die Farbwerte festlegt, um die orangene Farbe zu erkennen. Alle Pixel, welche innerhalb dieser Farbschwelle liegen, werden als weiß dargestellt, während alle anderen Pixel als schwarz dargestellt werden. Das Ergebnis ist ein Binärbild, in welchem die orangene Linie als weiße Linie dargestellt wird, während der Rest des Bildes schwarz ist (siehe Listing~\ref{lst:transform_pipeline}). 

        \begin{lstlisting}[caption={Ausschnitt aus der Verarbeitungspipeline}, label={lst:transform_pipeline}]
hsv = cv2.cvtColor(roi_frame, cv2.COLOR_BGR2HSV)
        
lower = np.array([0, 130, 60])
upper = np.array([30, 255, 255])

mask = cv2.inRange(hsv, lower, upper)
kernel = np.ones((7, 7), np.uint8)
mask = cv2.morphologyEx(mask, cv2.MORPH_CLOSE, kernel, iterations=2)
        \end{lstlisting}

        Durch eine nicht ausreichende Beleuchtung kann es zu Rauschen im Binärbild kommen, was die Erkennung der Linie erschwert. Um dieses Problem zu beheben, wird eine morphologische Operation namens \emph{Closing} angewendet, welche kleine Löcher in den weißen Bereichen des Binärbildes schließt und somit das Rauschen reduziert. Hierzu wird ein Kernel definiert, welcher die Form und Größe der Bereiche festlegt, die geschlossen werden sollen. Wie in Abbildung \ref{fig:stream4} zu erkennen ist, verbessert die Anwendung dieser Operation die Darstellung der Linie im Binärbild, da keine Löcher mehr vorhanden sind, was die Erkennung der Linie erleichtert.

        \begin{figure}[H]
            \centering
            \includegraphics[width=0.9\textwidth]{images/05Umsetzung/stream-4.jpeg}
            \caption{Darstellung des Bildes als Binärbild nach der Anwendung des Closing-Operators (Eigene Abbildung)}
            \label{fig:stream4}
        \end{figure}

        In Abbildung \ref{fig:stream4} lässt sich deutlich der ursprüngliche Klebestreifen erkennen. Es ist jedoch auch erkennbar, das umso weiter entfernt die Linie ist, die Erkennung schwieriger wird, da die Beleuchtung nicht mehr ausreichend ist und die Farbe an Sättigung verliert. Darum werden weiter enfterne Pixel eher als grau erkannt und schwarz eingefärbt, obwohl sie eigentlich orangefarbig sind und weiß sein müssten.

        Nichts desto trotz ist es für die Erkennung der Linie ausreichend. Mittels der Funktion \emph{findContours} von OpenCV können die Konturen der weißen Fläche im Binärbild erkannt werden. Wenn die Fläche der größten Kontur größer als ein bestimmter Schwellwert ist, wird die Kontur als gültiger Orientierungspunkt erkannt. Anschließend kann der Fehler berechnet werden. Dieser Fehler gibt die Abweichung der Linie von der Mitte des Bildes an. Je größer der Fehler, desto weiter ist die Linie von der Mitte entfernt. Dieser Fehler kann dann verwendet werden, um die Lenkung des Fahrzeugs entsprechend anzupassen, damit es der Linie folgen kann. In Listing~\ref{lst:conjurs} ist die Implementierung der Konturenerkennung und Fehlerberechnung zu sehen.

        \begin{lstlisting}[caption={Einzeichnen von Konturen und ermitteln des Fehlers}, label={lst:conjurs}]
contours, _ = cv2.findContours(mask, cv2.RETR_EXTERNAL, cv2.CHAIN_APPROX_SIMPLE)

if contours:
    largest = max(contours, key=cv2.contourArea)
    
    if cv2.contourArea(largest) > 100:
        M = cv2.moments(largest)
        cx = int(M["m10"] / M["m00"])
        
        error = cx - (width // 2)
        
        cv2.drawContours(roi_frame, [largest], -1, (0, 255, 0), 2)
        cv2.circle(roi_frame, (cx, int(M["m01"] / M["m00"])), 5, (0, 0, 255), -1)
        return roi_frame, error / (width // 2) * 100, 10.0
        \end{lstlisting}

        \subsubsection{PD-Regler}
        Nachdem der Fehler berechnet wurde beziehungsweise die Linie erkannt wurde, muss auf Basis dessen ein Steuerbefehl gesendet werden, um den Fehler zu korrigieren. Hierzu wird ein PD-Regler (siehe Abschnitt \ref{sec:pid_regler}) verwendet. Der Proportionalanteil des Reglers sorgt dafür, dass die Korrektur proportional zum Fehler ist, während der Differentialanteil dafür sorgt, dass die Korrektur auch von der Änderungsrate des Fehlers abhängt. Letzteres ist besonder wichtig, um ein Überschwingen zu vermeiden, da es sonst passieren könnte, dass das Fahrzeug über die Linie hinaus korrigiert und dann wieder zurück korrigieren muss, was zu einem unruhigen Fahrverhalten führen würde. In Listing~\ref{lst:pd_regler} ist die Implementierung des PD-Reglers zu sehen, welcher die berechneten Fehlerwerte verwendet, um die Lenkung des Fahrzeugs entsprechend anzupassen, damit es der Linie folgen kann.

        Zum Einstellen der Regelparameter $ K_p $ und $ K_d $ wurde ein Trial and Error Ansatz verwendet, bei dem eine vordefinierte Teststrecke mit verschiedenen Kurvenstärken befahren wurde, um die Auswirkungen der verschiedenen Parameter auf das Fahrverhalten zu beobachten. Durch die Anpassung der Parameter und das Beobachten des Fahrverhaltens konnte schließlich eine Kombination von $ K_p = 0.15 $ und $ K_d = 0.1 $ gefunden werden, welche ein stabiles und reaktionsschnelles Fahrverhalten ermöglicht, ohne dass es zu einem Überschwingen kommt. Zu beachten ist, dass die Korrektur durch den Regler nur die Lenkung beeinflusst. Die Geschwindigkeit bleibt konstant.

        \begin{lstlisting}[caption={Berechnung des Regelfehlers}, label={lst:pd_regler}]
processed, error, confidence = self.process_frame(frame)

if confidence > 0.0:
    derivative = error - self.last_error
    correction  = self.Kp * error + self.Kd * derivative
    self.last_error = error
    
    x = correction
    y = self.base_speed
else:
    x = 0.0
    y = 0.0
    self.last_error = 0.0

self.steeringCommand.emit(x, y)
        \end{lstlisting}
